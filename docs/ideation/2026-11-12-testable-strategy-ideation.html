Grounding Context

Codebase Context

  • The repo is early. It holds STRATEGY.md, ADRs 0001 to 0003, one requirements plan (core vocabulary and CLR review), and an empty plugin manifest. No skill, review, evaluation set, or fixture exists yet.
  • The four key metrics (STRATEGY.md lines 35-38) have definitions but no targets, owners, or data sources. "Findings acted on" and "Chain completion" have no source at all. The three milestones are "Not yet dated".
  • The plan defers the first test set and the false-finding threshold, because "no baseline exists today" (plan lines 93 and 123). Its acceptance examples AE1-AE6 (lines 83-88) are neutral Given/When/Then cases.
  • CI runs only dependency review plus one fitness-function precedent: scripts/check-upload-limits.test.mjs (node:test, 11 tests). Claude branches auto-merge on green CI, so any new required check gates merges.
  • ADR 0001 already uses competency questions as acceptance tests (CQ-01 to CQ-10). ADR 0003 records the CLR review as on by default.

Strategy lines the ideas must respect

  • Fixtures and examples are neutral: no real person, company, or private business figure.
  • The plugin judges logic only; the tool repo owns structure checks and file formats.
  • Resist a change that makes the CLR review optional by default, or starts a domain before the core vocabulary is stable.

External context

  • Strategy falsifiability practice: a leading indicator per guiding policy, triggers with thresholds and time windows, owners, review dates, and a decision register.
  • AI code-review evaluation: report catch rate per category, not one average; replay a regression corpus on each reviewer change; version prompt, model, and examples as one artifact. Benchmarks show the harness and prompt move scores as much as the model.
  • Assurance cases (GSN): a claim tree whose leaves carry evidence; tools flag undeveloped claims. Automated checks cover logic doubt; judgement covers epistemic doubt.
  • Analogies used: mutation testing, clinical pre-registration of endpoints, the drug-development Target Product Profile, radiology "satisfaction of search", and immune negative selection.

1. Strategy assurance case

Axis 4: the strategy's own logicConfidence 80%Complexity Low
Description
Give every line in STRATEGY.md a stable ID (for example P1 for Purpose, B3 for a Boundary, T2 for a Track, M1 for a Metric, MS1 for a Milestone). Write the strategy as a claim tree: Purpose is the problem, Positioning is the injection, each track's "Why it serves the approach" line is an arrow, and metrics and milestones are the evidence leaves. A small CI script then flags undeveloped claims: a track with no metric, a metric with no data source or no track, a boundary with no check. Run the plugin's own CLR review on the same tree by hand now, and with the skill later. Each finding becomes a strategy test to resolve. This tree is the natural core of QUALITY.md.
Basis
direct: STRATEGY.md line 44 says the review "maps the logic out of prose, such as a business or product strategy document, into a tree before it judges", and line 62 names "seeded strategy documents" as part of the evaluation set. direct: the orphans are real today. The Tool link track has no metric, and Domain extension appears only in milestone 3. external: GSN assurance cases flag undeveloped claims automatically.
Rationale
It turns "make the strategy testable" into a job the plugin already claims to do, and it gives the first concrete gap list. A logic tool whose strategy fails its own review is a credibility risk; finding the gaps first is the best demonstration of the positioning. It also states the surrogate claim the strategy relies on: eval-set scores lead to findings acted on, which lead to sounder decisions.
Downsides
The tree is a hand-built mapping until the prose-mapping skill exists, so the first review is manual. Stable IDs add a small editing cost to STRATEGY.md. Keep it a claim tree with real evidence links, not a "cartoon argument" with loose traceability.

2. Pre-registered metric charter: floor now, target after baseline

Axis 1: metric definitionsConfidence 85%Complexity Low
Description
Before the first evaluation run, commit a charter for each key metric: data source, denominator, owner, a binding floor set from first principles now (for example "no seeded insufficient cause missed in the first set"), a target left open until the first baseline run, and a decide-by date. Changes to a floor or target go through the decision register (an ADR), never an in-place edit. For the two session metrics, the source is a record contract, not telemetry: each finding carries a stable ID and a final disposition the author sets, and chain completion is read from the existing "which links a source does not answer" report. A tool then reports "floor met, target pending" instead of "no data".
Basis
direct: STRATEGY.md lines 35-38 give four metrics with no targets, and lines 74-76 leave all milestones "Not yet dated". direct: plan line 93, "The planner sets the threshold, because no baseline exists today." direct: STRATEGY.md line 50 already plans the unanswered-links report. external: clinical pre-registration of endpoints; the Target Product Profile's "minimum acceptable" and "ideal" tiers.
Rationale
It breaks the loop where milestones stay undated because thresholds do not exist, and thresholds do not exist because there is no baseline. A floor needs only an argument about what is unacceptable, so it can exist today. Fixing it before results arrive stops the goalposts from moving.
Downsides
A plugin has no runtime that collects sessions, so the session metrics stay local and opt-in; aggregate numbers depend on users sharing their records. Early floors may be wrong and need a recorded revision.

3. Evaluation-set factory from neutral seeds

Axis 2: evaluation setConfidence 80%Complexity Medium
Description
Build the evaluation set from a few neutral clean seed trees and a catalog of mutation operators, one per CLR category (remove a conjunct from an AND group, delete a negative branch, drop the AND NOT mitigation, make a cause restate its effect). Every mutant ships with its answer key and its repaired twin, so the review must flag the mutant and stay silent on the twin. Add two kinds of hard cases: valid constructs that look like defects (gates, AND NOT groups, long but sufficient AND groups) as the clean set, and trees with two or three defects of mixed categories, so a miss after the first finding shows up. Start with AE1-AE6 from the plan as the first seeds. Report catch rate per operator and per defect position, not one average.
Basis
direct: plan line 83 (AE1, "Late deliveries" with one cause "Too few drivers") and lines 84-85 (AE2, AE3) already describe insufficiency, missing negative branch, and AND NOT cases. direct: plan lines 66-68 (R9-R11) order insufficiency first and deepest, then side effects, then the gate and AND NOT patterns. external: mutation testing (mutants, mutation score); per-category catch rate in AI code-review evaluation; radiology's "satisfaction of search", where a second abnormality is missed after the first is found.
Rationale
Three of the four metrics depend on an evaluation set that has no first member. Operators make the set grow by running, not by hand-curation, which is where benchmark effort usually goes. Neutrality holds because every mutant comes from a neutral seed. Lookalike clean constructs keep the false-finding threshold honest on the trees where precision is hardest.
Downsides
Generated mutants can carry stylistic tells the review learns to spot, so some hand-written cases are still needed. AE1-AE6 trees are tiny, so they give a smoke baseline, not a real one. AE4 needs an unreadable-image fixture.

80%

4. Guardrail fitness-function suite

Axis 3: guardrail checks in CIConfidence 75%Complexity Low
Description
Extend the upload-limits precedent into a small node:test suite that turns the strategy's guardrails into failing checks. (a) Every tree-building skill runs the CLR review by default; no setting makes it optional by default. (b) Fixtures pass a neutrality lint: a pattern scan for currency figures, emails, and capitalized proper nouns outside an allowlist of invented names, with flagged items sent to a human review step. (c) No finding category in the plugin is a structure category the tool repo owns (loops, IDs, unconnected entities). (d) Plugin findings validate against the same finding schema as the tool repo's findings, so the Tool link track's "read alike" promise is checked.
Basis
direct: scripts/check-upload-limits.test.mjs already builds temp fixtures and fails a PR (11 tests). direct: STRATEGY.md line 31 (resist making the review optional by default), line 27 (neutral fixtures), line 24 (logic only). direct: ADR 0003 records the review as on by default. direct: plan line 116 assumes findings from both repos read alike.
Rationale
Claude branches auto-merge on green CI, so a guardrail written only in prose can be removed silently. The pattern already exists, so each check is a small increment, and the "Resist a change when" line becomes a refusal the repo performs.
Downsides
A name lint cannot list every real name, so it is a heuristic plus review, not a guarantee. Check (a) can only run once skills exist. Check (d) needs agreement with the tool repo on a shared finding format.

5. A delay counter-metric for "without delay"

Axis 1: metric definitionsConfidence 70%Complexity Low
Description
The brand promises "Deep deliberation without delay", but every key metric measures depth or completion. Add one paired counter-metric, for example findings shown before the first actionable one, or review turns per completed chain, with a band. Depth and delay then form a polarity with a limit on each side, so a higher catch rate cannot be bought by flooding the author.
Basis
direct: STRATEGY.md line 80, "Deep deliberation without delay", and line 82, "without analysis paralysis". reasoned: lines 35-38 hold four metrics and none measures time, turns, or volume of findings. A review tuned only for catch rate is rewarded for more findings, which the brand promises against.
Rationale
This is the most likely way the strategy fails while every listed metric looks green. It also matches ADR 0003's stated main risk: practitioners ignore a review that raises too much.
Downsides
A delay proxy is easy to game and depends on the depth-on-request design. It adds a fifth metric to a list the template advises keeping short.

6. Core vocabulary freeze with a stability clock

Axis 3: guardrail checks in CIConfidence 65%Complexity Low
Description
Define "core vocabulary is stable" as a check. Keep the core terms (tree types, logical kinds, connector meanings, the eight CLR categories) in a registry file with a content hash. CI allows additions and rejects a rename or redefinition. "Stable" means no breaking change across a set number of releases while the evaluation set stays at or above its floors. That state opens the domain track, and later a domain conformance kit proves milestone 3: the core evaluation set passes unchanged with the domain loaded.
Basis
direct: STRATEGY.md line 26, "Domains extend the core vocabulary; they never change it", and line 31, resist starting a domain "before the core vocabulary is stable". direct: line 76, milestone 3 "without a change to the core vocabulary". external: the Unicode stability policy, where encoded names never change but new characters can be added.
Rationale
"Stable" has no definition, so the resist rule cannot be tested today. This gives the domain track an objective start and reuses the same hash to prove milestone 3.
Downsides
No vocabulary file exists yet, so this can only be specified now. The plan defers domains, so the conformance kit is later work. The team must agree on the release count, which is a strategy decision.

7. Reviewer version ledger and a split "answered"

Axis 5: learning loop and governanceConfidence 60%Complexity Medium
Description
Treat the review procedure (skill prompt, vocabulary, evaluation-set version, model) as one versioned artifact. Append each evaluation run to a results ledger, by category and by version, so a release that lowers one category shows up even when the average rises. In the session record, split "answered" into "rebutted with a reason" and "answered without change". On a set cadence, decide for each rebuttal whether the review or the author was wrong, rewrite the pattern as a neutral fixture, and add it to the evaluation set. Start with the ledger; add a merge gate later, once runs are cheap and repeatable.
Basis
direct: STRATEGY.md line 37 counts "accepts, repairs, or answers" as acted on, so a rebuttal counts the same as a fix. direct: ADR 0001 lines 77-79 leave fail-versus-warn questions open, which a decision register would own. external: AI code-review drift practice (version the reviewer as one artifact, log disagreements by version); aviation near-miss reporting.
Rationale
Without versioning, a change in catch rate cannot be attributed to a cause, which is the very CLR problem the plugin teaches. Rebuttals are the only field evidence of false findings, and this loop lets the evaluation set grow toward real mistakes while staying neutral. It gives QUALITY.md a concrete job as the results and decisions ledger.
Downsides
Evaluation runs on a language model are costly and not fully repeatable, and need secrets in CI, so a merge gate is premature. The rebuttal loop needs field data and a person to decide each case.
